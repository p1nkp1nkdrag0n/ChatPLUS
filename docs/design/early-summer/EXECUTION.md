## 收尾修复与验收口径

初次实测发现原生 `loading=lazy` 会在未滚动时预取四章全部图片，桌面 3,518,232 B、手机 1,294,928 B，超过原首屏目标。改为保留图片 DOM，在所属章节首次真正进入视口后赋 `src/srcSet`；首章即时加载，离开后保留已加载图片。溪岸图片的 load 监听因此仍能正确建立命中 alpha，反滚也不重复加载。

复测首屏仅请求 7 个 S01/UI 资源：桌面 1,317,070 B（1.256 MiB），手机 537,156 B（524.6 KiB），分别落在 1.8 MiB / 900 KiB 目标内；估算活动图像 RGBA 为 29.5 / 9.75 MiB。两画幅均没有失败图片、API 请求或 console 问题，120 条场景采样无横向溢出，超出可滚动范围的目标点如实标记钳制。

独立审查还复现从使用说明底部点击官网链接会沿用旧滚动位置；现在非 POP 且无 hash 的导航回首屏并聚焦标题，浏览器历史和锚点保持自己的位置语义。

所有业务验证使用隔离 fixture 数据，截图中的晨风及文字是合成测试记录，不是用户私信。性能数字是 Windows Chromium 本机实验，不能替代真机、慢网络或现场用户数据。浏览器 720 CSS px / DPR 2 的重排检查不等同于真实 200% 缩放；OS 后台、触屏 pinch/旋转与低端真机不冒充已验收。

原包 `HANDOFF_QA.md` 只证明交付包。本轮结果不意味着原计划每个细分手绘资产、纸背补画、单独竖屏 master、流向图、逐花头延迟等已经完成；实现差异集中记录在生产对照表，便于后续精修。
