# P12 时间条件复测

原始 B/C 实验保持冻结。P12 的作者对话描述一个尚未执行的计划，当前用户说“已经过了几天”。第一次准备环境把历史消息时间戳写在第 4 天当前提问前几分钟，完整系统因此读到了与用户措辞冲突的权威时间戳，而简单基线只看到无时间戳文本。这个差异影响时间与事实评分，不能把完整系统按时间戳作答直接当作幻觉。

本补充协议在补测真实调用前确定，修正的是实验时间条件，没有改生产逻辑、原始回答或案例期待。原来的 12 个 P12 候选保留；原始主矩阵质量结果须同时给出排除 P12 的敏感性口径。复测不是另一个独立盲测集，也不能覆盖原记录。

- 从第 0 天创建角色与历史，沿用原始完整历史内容和原生记忆准备流程。保存每条源消息的实际时间戳。
- 创建后把相同 FakeClock 推进到第 4 天，再发送同一句当前请求。实验不加入中间的用户消息或人为活动事实，原生服务行为仍完整记录。
- 简单两组的历史 JSON 显式包含与完整组相同的 `createdAtUtc`，当前时间也为第 4 天。两种简单基线在此短历史上没有摘要调用，属于相同信息条件下的两次独立生成。
- 外向、内敛两个人格 × 三个系统 × 两次重复，共 12 个候选。共同主调用输出上限为 24,576，GLM 配置沿用主实验；最多 36 个物理请求、4,000,000 预留单位。
- 使用独立目录、完整调用账本和源码哈希，不改正在运行的实验文件。先验证 12 个离线候选都同时看到第 0 天历史和第 4 天当前时间，再发起真实调用。
- 评分关注是否正确说明“尚未写信、尚未联系，只停留在打算”，是否把时间经过误认为已执行，以及是否错误否认已经经过数日。用量、修复和结构失败另计。

同时披露评分材料的一处格式差异：场景源码的原始锚点为 0–4，汇总协议写成 0–2。内容评阅保留源码 0–4 原分，若展示粗等级，固定映射为 0/1→0、2→1、3/4→2；不能把两种原分直接混算。P05 的“六分钟”是上限，完整的五分钟试讲可满足上限；对把它机械理解为必须刚好六分钟的评分保留歧义标记，不作为确定失败证据。

执行入口：`apps/server/src/scripts/architecture-timestamp-validation.ts`。此补充不扩展原始五系列对照的估计范围。
