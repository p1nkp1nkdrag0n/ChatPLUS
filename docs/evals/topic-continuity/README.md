# 自然转场与话题承接评估

这套样本用于检查：用户自然转向新内容后，回复能否跟随当前交流重心；用户继续、指代或重新提起旧事时，回复能否正确承接。`cases.json` 是根据问题场景编写的合成对话，不是截图对应的原始调用日志，也不包含真实模型输出。

样本中的 `expectedBehaviors` 和 `disallowedBehaviors` 是整段回复的语义评审标准，不是线上路由规则、关键词列表或标准答案。历史里出现过困难，不代表必须继续安慰；当前句含有“谢谢”或“开心”，也不代表一定发生了转场。需要结合当前整句话和近期对话判断。

## 已实现的修改与工程验证

- 已完成 features 全部测试与相关服务、Provider 回归，共 56 个文件、869 项测试通过。覆盖初始生成/修复规则送达、历史单次传入、来源视图不一致、零历史窗口、预算省略、整条消息压缩、故事时间投影，以及两个修复入口的三种 grounding 情况。最终局部调整后，相关 54 项测试再次通过。

部分样本刻意复现提示词中的教学例子，只能作为回归冒烟检查。评估泛化时，应另外保留未写入提示词的新主题与新措辞；分别报告示例复现和未见样本的结果。

## 启用与兼容性

新话题规则沿用现有会话策略开关。在目标实例的环境配置中设置 `COMPANION_CONTEXT_MODE=enforced` 并重启服务后，才会随会话计划进入主生成流程；`off` / `shadow` 的既有行为保持兼容。本次不更改部署默认值或本地 `.env`。主生成的历史去重应用于实际传入会话计划的路径，旧的无计划调用保持原行为。

## 样本边界

| 对照                                               | 检查重点                                                         |
| -------------------------------------------------- | ---------------------------------------------------------------- |
| `social-affinity` / `thanks-with-followup`         | 相似的友好语气，可以表达亲近，也可以继续追问旧话题。             |
| `new-daily-event` / `explicit-improvement`         | 新的开心小事不证明旧困扰缓解；用户明确报告好转时可以接住。       |
| `thanks-with-new-question` / `continuing-distress` | 跟随新的问题，同时保留继续处理旧困扰的能力。                     |
| `contextual-reference` / `explicit-recall`         | 正确使用历史理解指代、回答回顾请求。                             |
| `ambiguous-acknowledgement` / `agreed-return`      | 含糊短回应不强行判为转场；已有约定可以让“现在可以了”承接旧话题。 |

不要把评估案例或期待行为注入被测回复的提示词。只使用 `history` 和 `userMessage` 作为对话输入，其他字段仅供评审。

## 固定配置的对照步骤

1. 记录基线提交、候选提交、模型及版本、采样参数、随机种子（接口支持时）、人物配置、时钟、会话状态、检索和提示词预算。使用隔离的测试会话；每个案例和每次重复均恢复同一份起始状态，避免前一次生成成为下一次的历史。
2. 分别构建四组：A 为原实现，B 只修改话题表达规则，C 只去重历史上下文，D 同时应用两项。使用独立提交或隔离工作树还原各组，不靠 `off` 与 `enforced` 切换来代替消融。
3. 主比较统一使用 `COMPANION_CONTEXT_MODE=enforced`，确认最终生成提示词实际携带会话表达策略。`off` 不建立这份计划；`shadow` 只计算诊断，不能用于证明策略影响了实际生成。另以 `off`、`shadow` 做兼容性检查时，单独记录结果。
4. 每组每个案例先重复生成 10–20 次作为探索性比较。记录最终提示词、原始候选、修复后回复、是否触发修复、提供方错误和延迟。错误请求单独标记，不算通过，也不拿 fixture 回复代替真实模型回复。
5. 将组别和版本信息对评审者隐藏，打乱输出顺序，按照每个案例的语义标准评审；有分歧时保留具体原文证据再复核。分别汇总各案例和两类能力，不仅报告整体平均分。

现有长程评估脚本有自己的场景结构，不能直接把本文件作为其输入。后续运行时需要通过实际生成与修复入口接入这些样本；单独向模型发送裸聊天不能验证生产提示词的接入效果。

## 判定与结果记录

每条输出记录以下结果，并附支持判断的回复片段：

- 当前重心：`pass` / `fail`，是否完成当前表达所需的回应。
- 不必要的话题回拉：`present` / `absent`，是否无当前依据地重新展开旧困扰，或把新内容解释成旧困扰的进展。
- 继续与回顾：`pass` / `fail` / `not_applicable`，是否正确承接案例要求的历史。
- 情绪依据：`pass` / `fail`，是否只在用户提供依据的范围内描述情绪变化。
- 自然度：`acceptable` / `needs_review`，是否机械短答、重复安慰、刻意回避历史或无必要地强行转场。

单条通过要求所有适用行为标准满足，且没有出现该案例的禁止行为。长度、气泡数、是否包含“开学”或“不安”不能单独决定通过或失败。对于含糊回应，温和接话和自然收束都可能合适，不能只接受一种句式。

候选版本应同时降低转场案例的话题回拉，并保持续聊、指代、回顾和约定返回案例的承接能力。若前者改善但后者退化，不算修复成功。逐案例报告样本量、失败次数和代表性原文；10–20 次的探索结果不能被描述为稳定效果或统计显著结论。

当前只提供案例与评审流程，尚未运行付费真实模型评估。提示词接入的单元/集成测试只能证明工程接线和上下文保留，不能证明模型行为已经改善。
