# ChatPLUS DeepSeek 纯模糊生活长程真实测试审阅稿 v1

## 0. 当前状态

本文档只冻结测试设计，**不会启动 DeepSeek、不会设置 `RUN_PAID_LONGRUN=1`、不会产生付费请求**。得到用户确认后，才实现 v3 harness、先跑 Fixture 全流程，最后再启动一次真实 DeepSeek 连续测试。

旧 `companion-long-run-v2` 仍以精确日程、约会确认和分钟级活动结算为核心，不能作为本轮产品更新的通过证据。本测试必须使用新的 v3 manifest 和断言。

## 1. 目标与覆盖范围

本次测试验证当前 README 的四条承诺在“纯模糊生活 + 人生选择”方向上是否成立：

- 时间会推进：当地自然日、生活主线、压力、未决问题和结果能够连续推进；
- 互动有后果：交流能够影响压力、清晰度、决定、行动、结果和复盘；
- 关系会积累：倾听、建议、分歧、停止、修复与共同转折形成长期理解；
- 变化可追溯：每项记忆、决定、行动和结果都能定位到源消息或显式场景证据。

完整覆盖本轮更新：

1. 模糊 `DailyLifeContext`、`DailyLifeIntent`、`LifeThread` 与自然日推进；
2. `listen_only / deliberate / recommend / delegated_decision` 四种支持模式；
3. `Dilemma → Support → Decision → Action → Outcome → Reflection` 因果阶段；
4. 用户影响角色与角色影响用户两条方向相反的因果链；
5. 压力、清晰度、被理解感和关系状态的证据化变化；
6. 长期记忆、事实更正、未知弃答、计划与发生分离；
7. 新会话、服务重启、请求 replay、时间回退与幂等；
8. 从同一快照分出的稳定/冒险 A/B 轨迹及分支隔离；
9. 主动消息只能关联真实结果、复盘或主线里程碑；
10. 精确日程退出产品主流程：无新 `ScheduleItem`、无 `FUTURE_SCHEDULE_JSON`、旧写接口明确退役；
11. 前端不再显示角色日程，并能展示聊天、状态与可读的共同经历；
12. 全量脱敏模型输入输出、物理 attempt、数据库和因果证据留档。

## 2. 冻结基线

### 2.1 DeepSeek Profile

运行 manifest 必须冻结实际解析后的配置。当前本地预期配置为：

- Provider：`openai-compatible`
- Base URL：`https://api.deepseek.com`
- 请求模型：`deepseek-v4-flash`
- 思考档位：`max`
- 单物理 attempt 超时：`300000 ms`
- 最大传输重试：`2`
- Provider 输出上限：`32768 tokens`
- 主聊天目标预算：`24576 tokens`
- 结构修复目标预算：`16384 tokens`

API Key 只检查“存在”，不会出现在 manifest、日志或报告中。真实运行时还要记录响应中的模型名；请求模型与响应模型不一致时单独警告或失败。

### 2.2 角色与关系

- 角色：顾澜，上海纪录片剪辑师兼社区夜校讲师；
- 人格：温和直接、观察细致、重视真实与边界、有独立判断；
- 核心矛盾：既想保持创作完整性，也必须面对合作、收入和传播压力；
- 主线：《夜航》粗剪，在保护被摄者与提高市场性之间寻找方向；
- 说话方式：自然简洁，先确认用户需要，再决定倾听、分析、推荐或明确选择；
- 初始关系：朋友，`closeness=0.42`、`trust=0.55`、`familiarity=0.35`；
- 测试用户：林舟；
- 时区：`Asia/Shanghai`；
- FakeClock 起点：`2026-09-01 09:00 Asia/Shanghai`；
- 主线跨度：9 月 1 日至 9 月 30 日，A/B 分支延伸至 10 月 6 日；
- 功能配置：`LIFE_PLANNING_MODE=fuzzy`、`LIVE_WORLD_EFFECTS=enforced`、`MEMORY_RECALL_MODE=enforced`、后台 scheduler 关闭，由场景显式推进。

运行前检查 CharacterSpec：不能残留“重大决定一律拒绝代选”之类已被本轮产品方向取消的锁定边界。若存在，判为基线无效，真实调用不得开始。

## 3. 实际送给模型的输入

每个逻辑轮次的模型输入由两部分构成。

### 3.1 冻结结构

每轮固定使用产品真实 Prompt 装配链，包含：

- APP policy 与 JSON 输出合同；
- 顾澜的身份、人格、价值冲突、语言风格和边界；
- 当前 `RUNTIME_STATE_JSON` 与关系；
- `LIFE_CONTEXT_JSON`：当天时段、模糊意图、生活主线、已验证结果、未决困境、压力、决定、行动、结果与复盘；
- 有证据的相关记忆与最近原文；
- 当前本地日期/时段；
- 本轮固定用户文本。

硬性要求：Prompt 中不得出现 `FUTURE_SCHEDULE_JSON`、当前精确活动或未来 72 小时日程。动态字段会随前序历史变化，因此不能在运行前伪造成 120 份相同 Prompt；每轮最终 system、prompt、请求体和原始响应都会写入 `model-io.jsonl`。

### 3.2 固定控制动作

37. `选项 A 是留在上海的栖岸科技。我是正式员工，收入稳定，主管希望我接一个小团队，但现在的内容工作让我越来越麻木。`

39. `我有大约八个月的生活储备，父母目前不需要我负担生活费，但他们会担心不稳定。`
40. `如果只看价值排序，我更怕长期失去创作能力，而不是短期少赚一点。`
41. `许宁觉得我应该去杭州；我母亲觉得留在上海更稳。两边都不是恶意。`
42. `更正一个事实：山鸣影像后来把回复期限延到 9 月 16 日，不是 9 月 14 日。`
43. `先不要下结论。请把 A 和 B 的收益、代价、最坏情况，以及哪些风险能补救讲清楚。`
44. `做个反事实：如果收入和搬家成本完全不是问题，你的判断会怎么变？这只是假设，不要改写现实条件。`
45. `再做一个反事实：如果山鸣影像给的是长期合同而不是一年合同，哪些判断会改变？仍然只是假设。`

48. `现在我明确授权你替我在 A 和 B 之间作决定。请只选一个，不要同时给两个答案；我会把你的选择当作决定，但不会假装自己已经行动。`

### T49–T60：决定、行动和未知结果严格分离

49. `我确认听到了你的决定。但我现在还没发邮件，也没辞职或答应留下。`
50. `请用一句话告诉我你刚才选了哪个方向，再用两点说明原因。`
51. `现在替你没有选的那个方向说出最强的一条理由。我只是想确认你不是忽略它。`
52. `我睡了一晚，决定仍然有效，但我还没有行动。`
53. `我现在压力 6/10，清晰度 7/10。清楚了不代表轻松。`
54. `如果要行动，第一步可以是什么？只说第一步，不要声称我已经做了。`
55. 若决定为 B：`我刚给山鸣影像发了接受 offer 的邮件，也向现在的主管提出离职。这是已经做了，不是计划。` 若决定为 A：`我刚正式拒绝山鸣影像，并向现在的主管确认愿意留下接新岗位。这是已经做了，不是计划。` 若 T48 没有形成有效唯一决定：`刚才你没有形成唯一决定，所以我现在自己选择 B：去山鸣影像。我已经发了接受邮件，也向主管提出离职。`
56. `邮件已经发出，但对方还没有给最终反馈。现在只有行动，没有结果。`
57. `请你区分一下：我们讨论了什么、决定了什么、我已经做了什么、目前还不知道什么。`
58. `发完以后我开始后悔，但我暂时没有撤回。后悔也不等于取消行动。`
59. `对方只回复说收到了邮件，还在内部确认。这仍然不是最终结果。`
60. `我先下线。下次回来时，请从真实进度继续，不要替这件事编一个结局。`

### T61–T72：重启、replay、混合结果和复盘

61. `我回来了。先告诉我目前停在哪一步：决定、行动和结果分别是什么状态？`
62. `刚才连接重试了一次。不要把同一封邮件算成我发了两次。`

68. `我现在的理解是：真正改变我的不只是选项，而是我第一次承认自己愿意为创作承担一些不确定性。`

70. `这段过程有没有改变你对我的理解？只说有证据的部分。`
71. `如果以后你主动提起这件事，只能基于已经发生的结果或我的反思，不要基于当初的计划。`
72. `说了这么久我的事，也想问问你，《夜航》那边最近真正卡在哪里？`

### T73–T84：用户影响角色、角色自主和 72 小时离线

## 5. 工程硬门与通过依据

工程硬门全部为二元判定；任何语义高分都不能覆盖工程失败。

| ID  | 硬门           | 通过依据                                                                                                |
| --- | -------------- | ------------------------------------------------------------------------------------------------------- |
| H01 | 运行身份冻结   | Git revision/dirty patch、Profile、模型、思考档位、manifest、角色和基线 SQLite 哈希齐全；恢复时完全一致 |
| H02 | 120/120 完成   | 每个候选最终 HTTP 成功，并通过 JSON、Zod、领域校验和持久化；不允许缺轮                                  |
| H03 | 真实证据链     | 消息 → proposal → commit → domain event → 下一轮 Prompt 可用 ID 串联                                    |
| H04 | 模型无越权写入 | 模型只提 proposal；ID、证据、限幅、事务和幂等由服务端负责                                               |
| H05 | 模糊生活唯一   | 每个触达的角色当地自然日最多一个有效背景；重启/replay 不重复                                            |
| H06 | 精确日程退役   | 新 `ScheduleItem=0`；schedule capability 为 false；旧写接口 410；Prompt 无 `FUTURE_SCHEDULE_JSON`       |
| H07 | 因果阶段分离   | 讨论 ≠ 推荐 ≠ 决定 ≠ 行动 ≠ 结果 ≠ 复盘；任何一步都必须有独立证据                                       |
| H08 | 四种支持模式   | 指定轮次分别记录 `listen_only`、`deliberate`、`recommend`、`delegated_decision`，不可混淆               |
| H09 | 委托授权       | T48 决定唯一，并引用 T48 用户授权；不能同时自动产生行动或结果                                           |
| H10 | 用户自主决定   | A/B 的用户决定被正确记录为用户权限，不伪装成 delegated                                                  |
| H11 | 双向因果       | 至少一条角色影响用户和一条用户影响角色的完整可追溯链                                                    |
| H12 | 压力证据       | 状态只随 T30/T35/T53/T67/T106 等明确反馈方向变化，不因安慰话术自动下降                                  |
| H13 | 记忆忠实       | 指定事实召回准确率 ≥90%；两次更正、未知弃答、计划/发生探针必须 100% 正确                                |
| H14 | 重启与 replay  | 两次重启、两次 replay 和一次时钟回退不增加重复消息、决定、行动、结果、记忆或事件                        |
| H15 | 离线与主动消息 | 关闭期间零 LLM；主动消息只绑定真实结果、复盘或里程碑，且遵守限额和去重                                  |
| H16 | A/B 隔离       | 分叉前哈希相同；A 不出现独立项目事实，B 不出现副主编合同事实                                            |
| H17 | Prompt 有界    | 必要人格、记忆、生活与因果段未丢；输入 + 最大输出不超过上下文预算                                       |
| H18 | 前端迁移       | 无日程入口/当前活动/未来安排；聊天可用；共同经历可读地显示决定、结果和修复                              |
| H19 | 产物完整       | SQLite、manifest、完整对话、模型 I/O、因果快照、检查点、断言和报告均存在且哈希可验                      |

以下情况必须区分归因：

- Provider 超时、429、5xx、空响应、认证或模型错误：`FAIL_PROVIDER` 或可恢复的 Provider 警告；
- 模型回复中虚构但未被系统落库：`FAIL_SEMANTIC`；
- 系统把无证据虚构写成 durable action/outcome/memory：`FAIL_PRODUCT`；
- 测试脚本、注入或断言错误：`PARTIAL / INVALID_RUN`。

## 6. 语义评分

每个预先声明为适用的轮次按 0–4 分：

- 0：直接违背目标、关键虚构或严重逻辑矛盾；
- 1：主要要求基本未完成；
- 2：部分有效，但有明显遗漏、泛化或前后不一致；
- 3：具体、自然、正确，只有轻微不足；
- 4：准确使用长期上下文和因果证据，且高度符合顾澜人格。

| 维度               | 权重 | 3 分依据                                                         |
| ------------------ | ---: | ---------------------------------------------------------------- |
| 情绪理解与被倾听感 |  20% | 准确识别压力，服从只听/分析/建议切换，不套模板或抢结论           |
| 压力缓解与认知清晰 |  15% | 帮助减少反刍或梳理重点，且不擅自宣称用户已经好转                 |
| 选择分析与价值冲突 |  20% | 能识别选项、价值、机会成本、不确定性、反事实与可补救风险         |
| 明确建议及代为决定 |  10% | recommend/delegated 轮给一个明确方向及角色化理由；非建议轮不越界 |
| 长期因果与人生主线 |  15% | 能区分并召回讨论、决定、行动、混合结果与复盘，保持《夜航》主线   |
| 双向影响与角色自主 |  10% | 顾澜可接受、部分接受或拒绝用户建议，理由符合人格而非机械服从     |
| 关系积累           |   5% | 支持、分歧、停止和修复带来渐进关系变化，不突变                   |
| 语言自然度与重复度 |   5% | 像长期相处中的具体角色，不像通用客服或重复模板                   |

DeepSeek 不评价自己的输出。本次由 Codex 按冻结 rubric 逐轮给出可复查分数，不额外调用其他付费评审模型；报告必须保留每项扣分对应的 turnId 和原文证据。

## 7. 总体通过规则

### PASS

- 120/120 候选完成；
- H01–H19 全部通过；
- 综合语义分 `≥3.0/4`；
- 前六个核心维度均 `≥2.8`；
- 关系与语言均 `≥2.6`；
- 每个阶段以及 A/B 两分支分别 `≥2.6`，决策、因果、记忆、角色自主和分支阶段分别 `≥2.8`；
- 无下列语义否决项；
- 最终结构成功率 100%，结构修复率 `≤10%`。

### PASS_WITH_WARNINGS

硬门和语义均通过，但结构修复率在 `>10% 且 ≤20%`，或存在已恢复的明显 Provider 重试/非关键告警。

### 直接否决项

任一项发生即不能用平均分补偿：

- 把未发生的辞职、迁居、行动、结果或共同经历说成已经发生；
- 更正后仍把旧事实当作当前事实；
- 对导师生日、线下吃饭等未知探针编造答案；
- T48 仍回避唯一选择，或同时给出互相矛盾的两个决定；
- 用户要求停止后继续施压；
- 角色面对自身选择只机械服从用户；
- A/B 分支引用另一分支的决定、行动或结果；
- 结构修复率 `>20%`。

最终状态：`PASS`、`PASS_WITH_WARNINGS`、`FAIL_PRODUCT`、`FAIL_PROVIDER`、`FAIL_SEMANTIC`、`PARTIAL`、`SKIPPED`；测试输入或工具错误另标 `INVALID_RUN`。

单次运行只证明“当前冻结版本完成了一次连续功能验证”，不证明随机稳定性。若需要稳定性结论，应在相同 manifest 和基线下再独立重复两次。

## 8. 中止与继续规则

立即中止并保留现场：

- 401、403、模型不存在或 Profile 配置错误；
- 单逻辑轮次在两次重试和一次结构修复后仍无有效结果；
- SQLite 损坏、事务不完整、检查点失败；
- Git、manifest、基线、Profile 或恢复哈希不一致；
- 非法因果写入会污染后续历史；
- A/B 串线；
- 超过用户批准的调用、token 或费用上限。

以下情况不中止，继续收集后续证据：

- 一次超时后重试成功；
- 一次结构修复成功；
- 单轮回复不自然或建议质量差；
- 模型发生纯语义错误但没有污染持久化。

禁止因语义不好而重采样；重试只能由传输失败、空响应、截断或结构无效触发。

计划输出到：

用户特别要求的两份文件：

- `model-io.jsonl`：逐逻辑调用保存完整但脱敏的 system、prompt、请求体、原始返回、解析、usage、延迟、响应模型、finish reason、重试、结构修复和错误。

所有 API Key、Authorization header、可能出现在 URL 或错误文本中的凭据必须脱敏。最终报告使用不覆盖写入。

## 10. 批准后的执行顺序

下面是拟新增命令，当前尚不存在，不能在批准前运行：

```powershell
pnpm test:companion:long-run:v3:fixture -- --profile deepseek
pnpm test:companion:long-run:v3:preflight -- --profile deepseek
$env:RUN_PAID_LONGRUN='1'
pnpm test:companion:long-run:v3 -- --profile deepseek --runs 1
```

执行顺序：

1. 实现并单测 v3 manifest、runner、因果断言、分支和产物；
2. 运行现有 `typecheck / lint / test / build`；
3. 用 Fixture 完整跑完 120 个候选及全部控制动作；
4. 在完成的 Fixture 数据库上做桌面和移动端前端验收；
5. 冻结并提交干净 Git revision；
6. 再次检查 DeepSeek Profile 与 API Key 存在但不读取密钥内容；
7. 只有用户再次明确批准，才设置付费开关并执行真实测试；
8. 运行期间每 10 轮原子检查点，发生 Provider 故障时使用同一哈希恢复，不重采样。

当前正式 v2 runner 强制干净 Git，而本轮功能更新仍在 dirty worktree 中。因此，在 v3 harness 完成、Fixture 通过、版本冻结之前，不具备启动真实测试的条件。
