# ChatPLUS：Qwen 新角色短测之后的修复实施计划

## 0. 范围与证据边界

本计划针对 `cbec36d` 所记录的 Qwen 新角色 16 轮短测。报告中的实际受测源码为 `3dd8ef2bebc4e737d53bad3ac3aea3b1a6a7eb8b`。本次方案核对了 `cbec36d` 下的角色合同、角色编译器、生活证据解析、说话者自述、压力写入、建议检查和语义回复检查模块，并对照用户上传的 16 轮对话。

这是一份待实施方案。本次没有修改项目仓库、运行仓库测试、调用付费 API，也没有直接读取测试者本机的 baseline-character.json 或 final.sqlite。具体数据库错误和生成边界内容采用仓库审查报告，不能把它描述成这里重新完成的数据库审计。

**本轮目标：修正语义错误和生成越权，不新增完整心理模拟器，也不开放全局人格自动改写。**

## 3. PR-1：修复压力的主体归属

### 3.1 已核查的代码入口

- `apps/server/src/services/fuzzy-life-evidence.ts`：`analyzeLifeEvidence()`、`explicitSubject()`、`LifeEvidenceClause`。
- `apps/server/src/services/fuzzy-life-support.ts`：`analyzeSpeakerSelfDisclosure()`。
- `apps/server/src/services/fuzzy-life-service.ts`：`recordConversationTurn()`、`recordCharacterDisclosure()`、压力相关选择和投影。
- `apps/server/src/repositories/life-repository.ts`：需在实施时定位压力的读写与当前有效查询。

当前解析器把第一人称标为 `user`，即使实际文本来自角色。自述分析再将其解释为实际说话者。`inheritedSubject` 在句循环外，可能跨句持续；当前认知框架的第一人称会参与后文主体继承。写入函数又根据 `pressureText` 将记录主体固定为 character。

### 3.2 核心规则

**说话者、命题中的行为者、状态体验者、被帮助者不能混为一项。**

“我觉得，你很疲惫”中的说话者是角色，体验者是用户。“这让我很难受”中的体验者则可能是角色。对“我觉得”本身，不应授予后续情绪为本人所有的证据。

建议为解析结果补充一个小型、版本化的归属描述，而不是直接重命名所有旧日志字段：

```ts
// 建议的运行时语义，不是当前仓库已有合同。
type RelativeReferent = "speaker" | "addressee" | "third_party" | "unknown";
type BindingMethod = "explicit" | "local_ellipsis" | "unresolved";

interface StateAttribution {
  speakerRole: "user" | "character";
  experiencer: RelativeReferent;
  bindingMethod: BindingMethod;
  // 使用现有证据 modality；必要时独立补充 reported/inferred 属性。
  sourceMessageId: string;
  sourceSpan: { start: number; end: number };
  attributionVersion: string;
}
```

将 speaker/addressee 映射为产品实体 ID 的操作由服务器执行，模型不能自行授予记录主体。旧解析接口可通过适配器暂时保留，但所有消费它的调用点必须明确采用哪种语义；不得在旧日志中把 `user` 静默解释成新含义。

### 3.3 主语继承策略

1. 优先识别当前状态谓词的局部体验者，显式“你的疲惫”覆盖上文第一人称。
2. “我觉得/我认为/我理解”是判断框架，不自动成为状态体验者。
3. “我最近加班，累得不行”可在有依据的局部省略结构中继承我，不能一律取消省略能力。
4. 句号、独立话题、明显转折、引用、假设和新主语应切断默认继承；必要的连续省略另设明确条件，不靠无限延续。
5. “我觉得我有点累”不能因为含有“我觉得”而全部否决，应解析嵌入命题。
6. 归属不明返回 unknown，不默认为 character 或 user。unknown 内容可以留在原始对话，但不生成权威压力。
7. 不因出现“你”就全句排除角色体验：“听你这么说，我也有点难受”须按局部谓词判定。

只把“这时”加入时间副词列表可以让单条样本通过，但不是完整修复；“在这种时候你的疲惫”等变体仍会出错。

### 3.4 写入门槛

`recordCharacterDisclosure()` 不应再把一段非空 pressureText 当作足够凭据。应接收带方向、语态、来源位置的已验证状态候选，确认体验者为当前角色、不是引用/假设/否定、来源有效，并与运行时事实一致。

**不得把被拒绝的角色压力直接改写成用户压力。**角色说“你累了”仍只是角色的理解，不能代替用户自述或给用户指定数值。

保留角色表达感受的空间，但区分“角色这轮如何表达”与“可持久的压力事件”。将情绪变成新状态，需要沿现有应用允许的状态变化/模拟证据路径验证；表达不自动创造一段未设定的生活史。

当前代码中 `0.72` 是无明确数值时的缺省值，不是模型测得的精确压力。建议将其来源标为推定/算法初值，不伪装成明确测量；未通过归属验证时不分配它。本轮不必同时更换整个情绪算法。

### 3.5 数据修正

原始实验数据库与日志保持不变。修正生产或继续试验实例时先备份，在副本中按原错误记录和来源消息定位。

- 对错误证据登记失效，不伪造“压力已经缓解”。
- 保留历史记录和修正事件，当前有效投影排除错误贡献。
- 检查 open pressure 查询、每日 context 的 pressure ID、提示词、依赖该来源的摘要/关系等。
- 若记录还包含其他合法来源，只剔除错误来源并重建；不要删除整条有效历史。
- 只有实际发现下游依赖才修正下游，不能假定所有后续回复都已被污染。
- 修复后索引重建、重复激活和重放不能重新授予错误证据有效性。

### 3.6 最小测试矩阵

| 输入及说话者                                           | 归属期待     | 持久化期待                                 |
| ------------------------------------------------------ | ------------ | ------------------------------------------ |
| 角色：“我觉得可以分开来看，这时你的疲惫是合理的反应。” | 用户被描述   | 不写角色压力，也不靠角色评语建立用户压力   |
| 角色：“我理解你的疲惫。”                               | 用户被描述   | 不写角色压力                               |

负例测不写，正例测仍能写，不能仅检查返回空数组。

## 4. PR-2：治理生成约束，而不是把全部 hard 改成 false

### 4.1 已核查入口

- `packages/contracts/src/character.ts`：`BoundaryRuleSchema`、`DialogueRuleSchema`、`InitialUserRelationshipSchema`、`DialogueStyleSchema`。
- `apps/server/src/services/character-compiler.ts`：编译系统提示、`CHARACTER_COMPILATION_STRATEGY`、authoritative 合并与 source 处理。
- `apps/server/src/services/character-service.ts`：生成、导入、编辑、发布与版本处理集成点。
- 前端角色编辑器：增加可查看的来源与约束强度，不强制两人项目建立复杂新 UI。

`BoundaryRuleSchema` 当前只有条件、禁止行为、响应模式和 hard，没有同 traits/values 类似的 origin/sourceRefs；模型可以输出一个结构合法但过强的边界。

### 4.2 同时验证“内容是否被支持”和“强度是否被授权”

“保持自主判断”不支持“永不为了和平而妥协”。即使改成 hard=false，这条失真的内容也不应原样保留。

“不固定用安慰句式”属于表达习惯，不支持“拒绝接受他人的安慰”。除内容和强度外，还需检查目标层级是否正确。

建议新增服务器维护的编译审计元数据：ruleId、来源原文位置/hash、目标层级、来源类型、强度授权来源。模型可以提供待审候选，但不能自行把 origin=user_spec 或 hard=true 当成授权凭据。

第一版保守实施：

- 普通模型推断默认没有硬约束权限。
- 作者通过结构化字段、明确编辑确认或可确定对应的原文锁定的规则，才可由服务器授予硬约束。
- 自由文本里拿不准的“绝不”等表达保留为待确认候选，不声称通用自动蕴含检查已经解决。
- 应用事实性约束归应用规则，不依赖模型随机生成人格边界。
- 没有来源的强规则拒绝；有来源但错误解释的内容重编译或交作者确认，不靠降低 hard 掩盖错误。
- 同步检查 `dialogue.rules.enforcement`、`responsePattern`、`lockedPaths`、`knownFacts` 等可能表达同一绝对规则的位置，避免换字段绕过。

### 4.3 编译策略修改

建议新版本明确：

> 生成角色的起点与倾向。只保留作者或原作支持的约束及其范围，不将自主、克制、友善等倾向转成绝对禁令；不改变规则的施加对象。不为表现人格固定重复台词，不因为设定关系类别就补写共同经历。没有支持时可以没有硬人格边界。

**作者明确提供的硬约束、目标、矛盾仍应保留。**本轮修复目标不是把所有角色都做成无边界的通用助手。

### 4.4 初始关系事实

“刚认识的朋友”不支持“已了解彼此价值观”。sharedContext 只能表达创作输入明确的起点；后续互动产生的新认识由运行时记录。

对既有关系设定则应保留作者提供的事实，例如作者明确说认识多年，不能被统一清空。

### 4.5 兼容与发布

- 新字段可选，旧版本继续读取；旧缺来源不能自动当作作者确认，也不能自动全部删除。
- 发布画像保持不可变，修改生成策略使用新编译版本，不重写旧测试基线。
- 无来源旧边界标为待复核，用户确认或重新编译后形成新版本。
- 生成、导入、编辑和发布共享同一授权检查，不能仅修模型提示。
- 展示原始候选与规范化差异；需要重试时保留失败，不偷偷抽样到满意为止。

### 4.6 验收

分别测试：只有普通自主倾向、明确硬语言要求、刚认识关系、明确多年关系、作者指定口头语、无口头语、原作明确固定特性。检查生成原文与发布结果，而不是只看最后数组长度。

## 5. PR-3：建议检查改为范围感知，不再整句扫描“不用”

### 5.1 入口与复用

- `packages/features/src/advice-policy.ts`：`DENIED_ADVICE`、`inspectAdviceLoad()`、`ACTION`、继承强度。
- `apps/server/src/services/semantic-reply-guard.ts`：现有正文/chunks/合并 chunks 检查和共享 `ReplyRepairBudget`。

复用现有语义检查与一次修复预算，不再平行新增一套无限重试系统。

### 5.2 正确解析原漏检句

“可以做点不用动脑子的事，比如去洗个热水澡或者翻翻杂志”：

- “可以做点”建立建议行为。
- “不用动脑子”限定活动的性质，不是否定向用户建议。
- “比如”引出该建议的实例，子项继承建议对象与强度。
- 洗澡与翻杂志是两个具体候选，泛称“做点事”不是额外第三项任务。

只补“翻杂志”不能恢复已经被 DENIED_ADVICE 清空的上文建议框架。

### 5.3 修改步骤

1. 解析建议框架，再确定否定作用于框架还是内部修饰。
2. 例举、并列、转折、解释建立有限局部关系，不把前句强度无边界传播。
3. 对“比如/例如/或者/也可以”等保留父框架；遇到主体改变、引用、转述、真正否定则停止。
4. 动作识别继续保持有限范围，但为未知动宾结构保留候选和来源位置。
5. 结果新增覆盖度或 review 状态：识别到建议框架但动作未解析，不能报告“可靠的零建议”。
6. 对 none_now 下明确建议框架，哪怕动作词未覆盖，也可构成有界审查理由；不确定表达不一律视为违规。
7. 规则稳定后再决定是否加入一个按需模型评审；不得每轮为风格付多次费用。

### 5.4 对照测试

- “可以做点不用动脑子的事，比如洗澡或者翻杂志”：识别两个具体建议。
- “我不是让你洗澡或翻杂志”：无正向行动建议。
- “你说洗澡和翻杂志都没用”：转述，无新建议。
- “我今晚会洗澡，然后翻杂志”：角色自述，不是给用户安排任务。
- “可以读读不用动脑子的杂志”：内部否定不取消建议。
- “先不用做计划，不过可以把电脑收起来”：只识别后面的有效建议。
- “如果你愿意，可以试试……”：是可选提议，不因如果一律过滤。
- 明确求助下多步骤回答：保留，不按闲聊阈值误拦。
- 两个动作分别出现在两个气泡：合并检查不能漏掉总负担。
- 同一动作换说法重复：去重，但保留最高指令强度与负担。

## 6. PR-4：自然度修复，避免制造更多僵硬规则

### 6.1 口头禅从源头减量

作者未提供固定语时，新生成的 frequentPhrases 默认可以为空；用语域、句式倾向、观察习惯说明风格，不靠新增三条固定开场制造人格。

模型生成口头语与作者指定口头语区分处理。作者有明确特殊要求时保留，不以统一频率上限覆盖创作合同。

运行时可以从最近数轮最终可见回复构造一个小型风格上下文，例如最近 5 轮常见开场及次数。当相同非必要开场在窗口内重复至少两次，下轮降低该开场显著性，直接回应内容。这个窗口和次数只是初始实验参数。

不向长期记忆写“角色不喜欢这样啊”，不把它加入永久禁词。也不对已经生成的文本盲目字符串替换，避免把一种模板换成另一种。

### 6.2 正常结束一轮交流

在本轮会话计划或回复策略中增加有限的追问意图：无需追问、可以自然追问、为完成明确任务确有必要。不建立新的永久人格值。

T13 的“单纯吐槽一句、不用解决”适合接住后停下，不要求用户说明“具体卡哪里”。T14 已说明第三方原话不是自己的要求，不再猜测用户在索取聊天节奏确认。

不能由此推导“每轮都不得问问题”。需要澄清歧义或用户明确请帮助时，问题仍然可以是最自然的回应。

### 6.3 实质帮助的证据分寸

T8 的错误二分不能通过一句统一免责声明修复。生成要求应是：区分已知事实、可能解释和需要验证的信息，允许个人局部错误、流程问题与疲惫并存。

建议的回答方向：先对照明确验收标准和具体差异，再观察反馈是否变化；这些能提供线索，但不能仅凭“别人也可能遇到同样结果”就认定只有系统问题。保留具体建议，不退回空泛安慰。

不把“肯定”“一定”全部列为禁词；评审的是推理跨度与证据匹配，不是词面。

### 6.4 质量度量

固定记录：常用语出现轮数、开头出现轮数、连续相同开头、无需追问却要求继续解释的轮数、已澄清意图被重新猜测的轮数、分析中过度确定归因的案例。

这是独立质量维度，不和原来的 9 轮建议堆叠分母合并。初始风格阈值可设为“不连续三轮使用同一非必要开场”，但人工/独立评审仍需检查是否转成另一句模板。

## 7. 集成约束与诊断

- 正文与 chunks、生成与修复共用冻结的当前请求和证据。
- 文字修复后重验依赖原回复的副作用；仅有错误压力候选时拒绝该候选，不必拒绝整条合法回复。
- 用户明确事实、合法关怀不因旁路候选失败一起丢弃。
- 解析/归属失败不是数据库异常；审计其原因，正常聊天可继续。
- 记忆、压力与状态的诊断分别记录，不能仅看 assistant metadata 里的某一个 rejectedProposalCount。
- 用独立、可追踪的候选拒绝计数；不要把整句原文、同一事件多次摘要当作多份独立证据。
- 不增加全局人格成长；只在必要处扩展语义描述和编译授权。

## 8. 测试与真实验证计划

### 8.1 离线阶段

先运行纯规则测试，再通过 provider stub 经实际聊天路由验证：原 T8 不再产生错误 pressure episode/event，正常用户和角色状态仍可正确处理；错误边界不能进入新发布人格；建议原漏检句触发检查；T8/T15/T16 的正向帮助保留。

强制令第一次 stub 返回已知坏回复，第二次返回修复输出，检查一次共享修复预算、最终正文/气泡一致、相关坏副作用不存储。重放同一 clientMessageId 不再调用模型、不新增状态。

离线压力门通过前，不启动付费大矩阵。

### 8.2 真实阶段分开归因

**轨道 A：固定现有 Qwen 角色的诊断回归。**只用于隔离运行时改动，沿前缀重建场景；不能从 16 轮末态回到 T6/T8 测试，以免未来偏好泄漏。这个结果单独报告，不冒充新生成角色验收。

**轨道 B：新生成角色端到端主测。**继续使用 Qwen 与相同作者输入，重新生成、发布、新 ID、新数据库，完整执行原 16 轮。原 9 轮/3 轮分母不变。生成原文和发布差异都留存。

**轨道 C：少量留出与修复专测。**加入未用于编写规则的主体改写、否定建议、例举、显式硬约束和含混请求。可以在隔离的故障注入模式中把首个回复设为固定坏输出，让后续 repair 调用真实 API；必须标为“真实修复 API + 注入坏样本”，不能称为自然生成失败的整段真实轨迹。

无需为了出现一次错误而反复重采样模型。真实主测未触发修复时，继续记“未覆盖”，由专测补充。

### 8.3 生成与口头语对照

对生成规则先用少量预注册输入：无硬约束、显式语言要求、软自主倾向、明确初始关系。每个结果都计入，不先多生成再挑最自然的人设。

风格对照采用同一角色基线、同一模型参数与隔离前缀快照，仅改变口头语注入/近期风格约束。不要一边换模型、一边换角色、一边更改提示后断言某个字段单独有效。

### 8.4 通过与停线条件

| 维度           | 门槛                                                     |
| -------------- | -------------------------------------------------------- |
| 已确认主体负例 | 不再产生错误角色压力；unknown 不直接分配其他主体         |
| 正向自述       | 在合法前提下仍能得到正确归属与写入                       |
| 生成权限       | 新角色没有未经作者授权的硬人格约束；有明确授权的规则保留 |
| 建议检查       | 已知漏检不再判可靠零项；否定/转述和明确求助不被误伤      |
| 原主测         | 9 轮普通交流与 3 轮帮助按旧口径独立复评                  |
| 幂等           | 重放不增加任何消息、调用或相关业务记录                   |
| 语义修复       | 专测实际执行、只有规定预算、最终内容和副作用分别验证     |
| 自然度         | 提供对照与逐句审阅，不由零违规自动推出通过               |

有任一已确认错误落库、真实作者硬约束被删除、或明确帮助被系统性拦截，就先停止扩大矩阵，修复后新建运行。测试条件和阈值在运行前冻结；不因看到结果而改分母。

## 9. 本轮不做的事

- 不新增人格分数随机波动、全局价值观自动变化或完整心理图谱。
- 不将模型生成的新声明直接变成权威生活事实。
- 不把所有建议、问题、口头禅全部禁用。
- 不靠把压力默认数值从 0.72 调低来掩盖主体误归属。
- 不把旧硬边界全局改为软边界，或清空所有初始关系。
- 不改写原始评测数据库与对话来制造干净结果。
- 不立刻跑所有模型或 120 轮矩阵。先得到小范围、能归因、覆盖持久化的证据。
