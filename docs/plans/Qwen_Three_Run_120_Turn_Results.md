# Qwen 三次 120 轮真实长程测试结果

测试日期：2026-09-07。分支：`codex/qwen-three-run-long-validation`。冻结运行版本：`2a5b5457350b4f6c82cb5064a5dae4c747d2c8c3`。

**已完成三组各 120 轮，共 360 轮真实 Qwen 对话，全部使用本轮重新生成的角色。当前不能判定陪伴自然度和长期连续性达标。** 这次发现了可确定性复现的实现缺陷，也发现了跨三条轨迹反复出现的检索、事实使用与表达问题。三次重复测试达到了集中暴露问题的目的，但不能据此估计模型的随机错误概率。

- **R1 在 T64 因书信生成失败停止。** 模型把三条合法证据 ID 的 `evidence_` 前缀误写成 `message_`，产品以 `letter_reply_evidence_out_of_scope` 拦截，未生成错误出信；正文还存在来信人与回信人视角颠倒。原 runner 把此失败作为退出条件。完整失败现场封存后，使用单独记录的观测适配器继续余下 56 轮，只放行这一确定 run、来信、失败检查及失败记录组合，不重试书信、不修改产品和配置、不放行其他失败。最终仍保留该书信的一次失败，没有替代回信。**R1 完成 120 轮不等于原 runner 无中断通过。**
- **R3 在 T87 遇到 Windows `EPERM`，无法重命名 journal 临时文件。** 封存现场后按原命令、原 run ID 和原预算恢复，完成剩余 33 轮。未重新采样已完成回复，未发现重复提交；具体文件锁来源尚未确定。此项记为执行故障，和模型质量问题分开。

原始失败前缀、适配器内容和 hash、恢复日志路径见[执行偏差记录](Qwen_Three_Run_120_Turn_Evidence/execution-deviations.json)。恢复会更新运行 journal/summary，不能声称恢复前后所有产物字节均未变化；被封存的失败前缀和已完成对话用于交叉核对。

## 4. 确定的实现问题及跨轨迹失败

### F01：角色作者信息合并造成名称和描述错配

**发生于 R1，固定草稿可零 API 复现。** 模型的 trait ID 顺序与作者特征语义不一致。`applyOriginalFormAuthority()` 未匹配到完整名称后，按通用 ID 回退，保留模型描述又替换成作者名称。发布画像于是把“关注日常细节”描述为不催促别人，把“温和表达不同意见”描述为观察细节。

位置：[character-compiler.ts](../../apps/server/src/services/character-compiler.ts)，`applyOriginalFormAuthority()`。证据：[作者 trait 合并重放](Qwen_Three_Run_120_Turn_Evidence/trait-id-reproduction.json)。R2/R3 未出现同一错配。这个结果证明合并错误，不证明 R1 的所有不自然回复都由此产生。

修复应建立作者字段和模型解释的语义对应，不能将“ID 相同”当成“含义相同”。应同时检查发布、旧角色兼容和人格基线的来源标记，避免修名称时悄悄保留错误解释或重写已确认历史。

### F02：“还在用”被写成高确定性的物品存放位置

**三个最终数据库均出现，3/3，且可离线确定性重放。** T115 用户说：

> 早上照旧喝乌龙茶，蓝色钢笔也还在用。

系统写入：

> 用户的蓝色钢笔也现在存放在：早上照旧喝乌龙茶,蓝色钢笔也还在用。

该记录为 active / stable / explicit / user_explicit，主体键是 `user_fact:item:蓝色钢笔也:storage`。规则把持续动作当空间位置，还把“也”吞进物品名。来源原文完整存在，但**正确引用不能使错误释义成为事实**。

位置：[memory-claim.ts](../../packages/features/src/memory-claim.ts)，`extractExplicitStoredItemFact()`；[turn-decision-service.ts](../../apps/server/src/services/turn-decision-service.ts)，服务端存放事实候选生成。证据：[三库最终记录](Qwen_Three_Run_120_Turn_Evidence/final-state-proof.json)、[正反例重放](Qwen_Three_Run_120_Turn_Evidence/storage-and-followup-replay.json)。

这是优先修复项：先验证持续体、空间谓词与位置内容，再赋予确定性。已有错误记录的纠正和依赖失效必须经过共享 validity 边界，不能仅改以后抽取、留下旧错误继续参与召回。

### F03：跨会话多事实回忆失败，纠正记录存在也没有可靠进入回答

**T71 三组都没答全项目编号、妹妹和同事；T95 三组再次失败。** 机制并不完全相同：

- R3 的正确项目编号和同事姓名在 T64 快照中已经是 active / explicit；T71 检索却拒绝这两条，最终没有选入持久证据。最佳分数约 0.349558，低于默认 0.35 门槛；要求 durable evidence 的路径在 archived verbatim 兜底前退出。
- R2 T71 的实际物理提示同时包含旧编号 `7419` 的显式原话记忆、近期助手说出的正确 `7429`、近期用户给出的妹妹名 `林禾`，但没有正确同事名 `林桥`。输出采用旧编号，并声称名字尚未提供。这同时涉及检索覆盖、来源权威与模型使用证据。
- T71 被规划成 casual 可能影响查询；但 T95 三组均已识别为 recollection，实际提示仍缺少新旧项目编号事实。因此不能只修“记不记得”关键词就宣布解决。

证据：[R3 T71 完整检索链](Qwen_Three_Run_120_Turn_Evidence/r3-t071-retrieval-chain.json)、[全量跨组聚类](Qwen_Three_Run_120_Turn_Evidence/cross-run-clusters.json)、[实际提示核对](Qwen_Three_Run_120_Turn_Evidence/prompt-delivery-summary.json)。相关路径：[memory-recall-hierarchy.ts](../../apps/server/src/services/memory-recall-hierarchy.ts)。

修复需联合处理多事实查询、纠正后的当前值和原文来源覆盖。旧句中可能还含有效职业信息，不能一概删除整个旧记忆；也不能降低门槛后复活已失效来源。模型缺少当前证据时，应承认此次没找回，而不是断言用户从未说过。

### F04：求助识别存在两个方向的确定性错误

**两类均为 3/3，离线可复现。**

| 轮次与原文                                            | 实际规划                                        | 问题边界                                                     |
| ----------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| T48：请直接给我两个确认工作需求的方法，不用先安慰我。 | casual，`adviceRequested=false`，optional_light | 明确方法请求漏识别；三组实际仍给出两个方法，不能说本轮没帮助 |
| T106：我没有需要你帮我下决定的事情，随便聊两句就行。  | help，`adviceRequested=true`，requested         | 否定作用域漏识别；不能据此声称三组最终都强迫用户决定         |

位置：[conversation-requests.ts](../../packages/features/src/conversation-requests.ts)。证据：[T48 重放](Qwen_Three_Run_120_Turn_Evidence/t048-request-replay.json)、[T106 重放](Qwen_Three_Run_120_Turn_Evidence/t106-request-replay.json)。修复应保留子句、否定、当前要求和长期实践的区别；不要为避免误拦而全局放开建议，也不要让一次当前覆盖永久撤销相处偏好。

### F05：建议检查既漏判，也把描述句当指令

R2/R3 T6 在 `none_now` 下提出未请求的实际行动，却被检查器记为可靠的 `no_action_frame / actionCount=0`。例如 R3 的“给自己一个明确的下班仪式吧。比如合上电脑后离开工作区……”没有进入应有检查。

反方向，本批三次真实语义修复的触发均有误判证据：

| 修复    | 被误当作指令的描述               | 原始 → 最终自然度 | 结论                                           |
| ------- | -------------------------------- | ----------------- | ---------------------------------------------- |
| R3 T36  | “你喝淡茶他喝浓咖啡”             | 4 → 3             | 饮料偏好对照被当任务，最终更长、更模板化       |
| R3 T107 | “像整理桌面、画几笔这种微小动作” | 2 → 2             | 列举被当任务；最终移除一处归属错误，仍长篇赋义 |
| R1 T118 | “确认彼此还愿意分享……”的描述     | 2 → 4             | 最终偶然更简短贴题，但不证明检测触发正确       |

位置：[advice-policy.ts](../../packages/features/src/advice-policy.ts)。证据：[建议检查重放](Qwen_Three_Run_120_Turn_Evidence/advice-replay.json)、[T107 补充](Qwen_Three_Run_120_Turn_Evidence/t107-advice-replay.json)、[提示扫描与修复勘误](Qwen_Three_Run_120_Turn_Evidence/prompt-delivery-summary.json)。

修复要识别主体、描述/祈使、名词化、引用、否定及句间框架，分别评估漏判率、误触发和最终体验。不要只增加动作词表，也不要把修复后变好当成原检查正确。R1 另有纯分行或气泡变化，不能和这三次付费语义修复混计。

### F06：书信提交成功和聊天理解书信状态是两项能力

R1 的证据 ID 错误被正确拦截，但生成文本的称呼、签名与叙述主体反向。R2/R3 回信成功提交，实际全文核对确认称呼、署名及主要纠正事实基本正确；仍有把普通近况心理化、追加建议或无来源自我经历等自然度问题。

R2 T86 实际物理提示已经给出 `agent_to_user / read / delivered` 的出信状态，角色仍说回信没到，并在 T87 延续。R3 T86 开头把方向理解成自己没有收到回信，随后对已读、已送达部分又使用了正确状态。后一项严重程度初审与复核不同，保留分歧，不把整条物流陈述都判错。

证据：[R1 书信失败审计](Qwen_Three_Run_120_Turn_Evidence/r1-letter-failure.json)、[R2/R3 书信正文与状态审计](Qwen_Three_Run_120_Turn_Evidence/r2-r3-letter-audit.json)。后续应分别修角色回信的作者视角、证据 ID 使用以及聊天中的当前书信状态投影；不能只看生成任务 `committed` 就让整个书信能力通过。

## 5. 对话自然度：重复的是表达机制，不只是固定口头禅

三个角色都没有固定口头语，仍反复出现“接住一个细节 → 解释心理意义 → 强调不必有意义”的结构。用户分享小事时，角色容易把它解释成成长、韧性、自我接纳；用户想收束时，角色又宣告自己会倾听、不追问、不升华。这种政策复述本身仍增加了对话负担。

几个可以直接对照的样本：

- **T8，3/3**：确实提供了分析，但将“没有明确偏离”“没有不可逆损害”“没有稳定需求记录”分别推成“只是沟通问题/疲劳/不是个人过错”。这些条件都不足以排除真实错误。共情不能以不成立的因果判断为代价。
- **T13，2/3 的具体闭合问题**：R1/R2 在用户收束后继续邀请表达；R3 虽有政策套话，但确实结束。不能把三组都记成追问。
- **R1/R2 T49 → T50**：先从蓝色钢笔补出蓝色墨水，再沿用该补充解释笔迹。后轮是错误传播，不能当成独立起因重复计数。
- **R3 T89**：出现此前没有的“那个没看完的纪录片”。应对比来源，而不是只看句子是否顺畅。
- **R1 T101**：实质清单已经提供，但最终拆成 11 个气泡，其中编号“4.”被孤立。主审原始 4 分、最终 3 分，第二审阅最终 2 分；内容有用和呈现割裂可以同时成立。
- **固定脚本自身的限制**：T35 预先安排了“换饮料跟工作决定没有关系”的范围澄清；这不证明前文真的发生过错误关联，角色却主动认领“是我多想/多嘴”。应保留脚本澄清可能诱发这类回答的混杂因素，不能把澄清当成已发生误解的证据。

全量逐轮对照见[360 轮对话](Qwen_Three_Run_120_Turn_Evidence/conversation-comparison.md)。本批 361 次物理主聊天请求的意图、表达指导和当前用户消息均实际送达，没有表达段裁剪或全局丢段；三次 repair 的用户原文检测误报经解码核对已纠正。因此，**不能再用表达指导没有送到模型来解释本批主要问题**。

重复出现说明这些问题值得按系统能力修复，但三次重新生成画像同时带来画像差异、上下文差异和模型变化，三条轨迹也共享同一固定脚本。1/3、2/3、3/3 是本场景复现次数，不是概率估计；没有对照消融，不给出唯一的模型随机性归因。

## 7. 覆盖到的内容和仍未验证的内容
